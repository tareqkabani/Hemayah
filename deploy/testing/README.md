# حزمة اختبار البيئة — اختراق وضغط

سكربتاتٌ جاهزةٌ لاختبار البيئة التجريبية قبل الانتقال للإنتاج. **كلّها تعمل عبر
Docker** — لا تثبيت أدوات على جهازك. التقارير تُكتب في `deploy/testing/reports/`
(مُتجاهَلٌ في git — قد يحوي تفاصيل ثغرات).

> **أين تُشغَّل؟** أدوات الاختراق والضغط تضرب النظام **من الخارج** كما يفعل
> مهاجم، فتُشغَّل من جهازك أو جهاز الفاحص لا من السيرفر. الاستثناء الوحيد
> **Trivy** — يفحص صور Docker محليّاً، فيُشغَّل على السيرفر حيث الصور.

> **⚠️ إذنٌ مسبق:** الفحص النشِط (ZAP `--full`، sqlmap) يرسل حمولات هجومٍ حقيقيّة.
> لا يُشغَّل إلّا على بيئةٍ ببياناتٍ وهميّة، بإذنٍ مكتوبٍ من مالك النظام، وخارج
> أوقات المختبرين. الفحص السلبي (baseline، testssl، nmap) قراءةٌ آمنة.

## البدء المُرشَّح — ثلاث أدوات

```bash
cd deploy/testing

# 1) TLS والشهادة (قراءة آمنة)
./scan/testssl.sh hemayah.pp.gov.sa

# 2) ثغرات الويب — فحصٌ سلبيٌّ آمن
./scan/zap-baseline.sh https://hemayah.pp.gov.sa

# 3) ضغط — دخان أوّلاً ثمّ الرحلة
docker run --rm -i grafana/k6 run - < k6/smoke.js   -e BASE=https://hemayah.pp.gov.sa
docker run --rm -i grafana/k6 run - < k6/journey.js -e BASE=https://hemayah.pp.gov.sa -e VUS=10
```

## اختبار الاختراق — `scan/`

| الأداة | السكربت | ماذا يفحص | الوضع |
|--------|---------|-----------|-------|
| testssl.sh | `testssl.sh <host>` | إصدارات TLS، الأصفار، الشهادة | آمن |
| OWASP ZAP | `zap-baseline.sh <url>` | ثغرات الويب (سلبي) | آمن |
| OWASP ZAP | `zap-baseline.sh <url> --full` | فحصٌ نشِطٌ مهاجِم | ⚠️ إذن |
| nmap | `nmap-ports.sh <ip[,ip]>` | المنافذ والخدمات المكشوفة | آمن |
| Trivy | `trivy-images.sh [supabase]` | ثغرات صور Docker (على السيرفر) | آمن |

**غير مُسكربَت (يدويّ عند الحاجة):**
- **sqlmap** — حقن SQL على مسارات الـAPI. سطحنا صغير: كلّ الوصول عبر RPC وRLS،
  والمدخلات مُتحقَّقة بـ zod. جرّبه على معاملات المسار مثل `?ref=`:
  `docker run --rm sqlmapproject/sqlmap -u "https://hemayah.pp.gov.sa/api/v1/cases?status=1" --headers="Authorization: Bearer <token>" --batch --level=2`
- **Nikto** — إعدادات خادم الويب: `docker run --rm sullo/nikto -h https://hemayah.pp.gov.sa`
- **Burp Suite Community** — فحصٌ يدويٌّ متقدّم (واجهة رسوميّة، يُثبَّت على الجهاز).

## اختبار الضغط — `k6/`

| السيناريو | يقيس |
|-----------|------|
| `smoke.js` | طلبٌ لكلّ نقطةٍ عامّة — تأكيد الحياة قبل الحمل |
| `journey.js` | دخول نفاذ + قراءة القضايا/الإشعارات تحت تزامن |

**⚠️ حدّ المعدّل يحكم قراءة النتائج:** بوّابة الـAPI تسمح **120 طلباً/دقيقة لكلّ
IP** (`apps/api/src/middleware/rate-limit.ts`) بمفتاح `X-Forwarded-For`. من مصدرٍ
واحدٍ يعني ذلك ~2 طلب/ث قبل أن تردّ `429` — وهو **السلوك الصحيح لا عطل**.
`journey.js` يعدّ الـ429 في عدّاد `rate_limited` منفصلٍ ولا يحسبه إخفاقاً.

لقياس **السعة الحقيقيّة** للطبقات (لا حاجز المعدّل):
- شغّل k6 من عدّة أجهزة/مصادر IP، أو
- ارفع `MAX_PER_WINDOW` مؤقّتاً على **التجريبيّة وحدها**، أو
- استهدف صفحات الواجهات (`smoke.js`) التي لا تمرّ ببوّابة الـAPI.

لا تُزوّر `X-Forwarded-For` لتجاوز الحدّ في اختبار الحمل — ذاك اختبار اختراق
(تجاوز ضابط أمني)، لا اختبار سعة.

**قياس القاعدة تحديداً:** `pgbench` على سيرفر القاعدة —
`docker exec -it supabase_db_Hemayah pgbench -U postgres -c 10 -T 60 postgres`

## بعد كلّ جولة

1. راجع التقارير في `reports/` — رتّب حسب الخطورة (CRITICAL/HIGH أوّلاً).
2. الثغرات الحقيقيّة → تذكرة إصلاح؛ الإيجابيّات الكاذبة → وثّقها كي لا تتكرّر.
3. لا تُضِف محتوى التقارير إلى git (فيها تفاصيل قابلة للاستغلال).
